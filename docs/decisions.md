# 智能客服系统 · 重要体验取舍

本文件只记录会改变等待方式、结果质量、可恢复性或界面行为的选择。常规实现细节见 `docs/tech-spec.md`。当前实现以已确认选择为准。

## D-001 员工端刷新后能否继续同一会话

- **日期与状态**：2026-09-12；已确认。
- **关联**：REQ-001、REQ-003；AC-005、AC-006、AC-019、AC-020、AC-021；API-007、API-009、API-010；tech-spec §一、§二 API-007、§三、§五、§六。
- **问题与体验影响**：全系统只有一套登录账号，员工端不做历史会话列表。刷新、误关标签页或再次进入员工端时，当前对话（含反问轮次、改写记录、是否已转人工）是否还在，会直接改变员工和客服的操作方式。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 本浏览器记住当前会话 | 刷新可继续同一条对话和转人工状态；关掉标签页或清站点数据后再进员工端会开新会话。换一台电脑无法找回。实现上用 `sessionStorage` 保存 `conversation_id`。 | 不增加员工端历史列表，符合 PRD 非目标。同一共享账号下靠会话编号隔离，不靠用户身份。 |
| B. 每次进入员工端都开新会话 | 刷新即丢失当前对话；若已点转人工，员工刷新后会进入一条新的未转接会话，客服仍只能在原会话里回复，两边对不齐。实现更简单。 | 与 AC-005/AC-006「同一条对话」在刷新场景下冲突风险高。 |

- **建议及理由**：选 A。转人工后必须保证员工和客服还在同一条对话里；刷新丢会话会把已转接状态拆开。放弃 B 换来的实现简化。
- **最终选择与确认依据**：A。2026-09-12 用户回复「1.A 2.B 3.A 4.A」。确认上下文：主智能体就四项体验取舍征询用户后回传本实例。
- **落地与验收**：API-007 仅在 `sessionStorage` 无有效 `conversation_id`（或 GET 详情 404）时创建；刷新后员工端用同一 id 拉 API-009，反问轮次与转人工状态仍在。测试尚未执行。
- **复议条件**：若后续要求员工端历史列表或按人分会话，需要重议。

## D-002 知识入库是当场等完还是后台进行

- **日期与状态**：2026-09-12；已确认。
- **关联**：REQ-002；AC-003、AC-004、AC-017、AC-018；API-003～API-006；tech-spec §一、§二、§三、§五、§六、§七。
- **问题与体验影响**：入库要分块、调模型打标和抽 FAQ、再写向量。用户在知识库页提交后，是卡住等到结果，还是先离开、回头再看。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 同步等完 | 提交后页面保持加载，成功则立刻看到该文档标签和 FAQ，失败则看到「请重新上传」。中途刷新会中断这次请求，需重新上传。一篇中等 Markdown 估计等待约 10–60 秒（随文档长度和模型耗时变化，待真实验证）。 | PRD 主流程是线性的「上传 → 看见标签/FAQ」，无需任务列表。 |
| B. 后台入库 | 提交后立刻看到「入库中」，可去其他页面；完成后才能改标签/FAQ。需要状态展示和定时拉取。失败仍提示「请重新上传」。等待感受更短，但界面和实现都更重。 | 阶段 B 必须做进行中/失败态；进行中文档不得进入 FAQ 或召回。 |

- **建议及理由**：当时建议 A，与 PRD 线性主流程一致。用户未采纳。
- **最终选择与确认依据**：B（与建议不同）。2026-09-12 用户回复「1.A 2.B 3.A 4.A」。确认上下文：主智能体就四项体验取舍征询用户后回传本实例。
- **落地与验收**：API-003 校验通过后立即返回 `ingest_status=ingesting`，后台完成后再变为 `ready` 或 `failed`。知识库页与列表用约 3 秒拉取（与 D-003 同一间隔）刷新状态。`ready` 前不可改标签/FAQ，也不可被提问命中；失败文案仍为「请重新上传」。AC-003/AC-017/AC-018 在变为 `ready` 之后验证。测试尚未执行。
- **复议条件**：后台任务在进程重启后大量残留「入库中」，或用户希望取消进行中的入库。

## D-003 客服端和新消息如何更新

- **日期与状态**：2026-09-12；已确认。
- **关联**：REQ-003；AC-005、AC-006；API-008、API-009、API-012；知识库进行中文档亦复用同一间隔；tech-spec §五、§七。
- **问题与体验影响**：转人工后，客服何时看到新会话/新员工消息，员工何时看到客服回复。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 前端定时拉取 | 客服列表和双方对话最多延迟一个拉取间隔（建议 3 秒）才出现新内容。实现简单，和现有 JSON 接口一致，不依赖长连接。 | Vite 已预留 `/ws` 代理，但本方案用不到。间隔写入 config。 |
| B. WebSocket 即时推送 | 新会话和新消息几乎马上出现。要实现鉴权、心跳、断线重连；刷新或网络不稳时仍需回退到拉一次全量。 | 规范允许 `/ws`；复杂度和联调成本更高。PRD 未要求「即时」。 |

- **建议及理由**：选 A。内部客服可接受数秒延迟；先把转接与回复做对。放弃即时性，换稳定和更少联调面。
- **最终选择与确认依据**：A。2026-09-12 用户回复「1.A 2.B 3.A 4.A」。确认上下文：主智能体就四项体验取舍征询用户后回传本实例。
- **落地与验收**：员工端（已转人工）、客服端列表/详情、知识库「入库中」文档均按 `poll_interval_ms=3000` 拉 API-008/009 或 API-004/005。不实现 WebSocket。测试尚未执行。
- **复议条件**：现场使用中延迟被明确抱怨，或后续要做多客服同时在线。

## D-004 「同一问题链路」在员工换题时是否重置反问轮次

- **日期与状态**：2026-09-12；已确认。
- **关联**：REQ-001；AC-019、AC-020、AC-022；API-010；tech-spec §五。
- **问题与体验影响**：同一会话里已经反问了若干轮后，员工突然改问一个已经说清楚的新问题（或问候）。系统把这句算作旧链路的下一轮，还是当作新问题立刻检索。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 改写后已可处理则重置轮次 | 员工中途换题，只要问法清楚，立刻走 FAQ/闲聊/检索，不必先凑满 5 轮。含糊追问仍累计，满 5 轮后再含糊则兜底。 | 符合「5 轮内一旦说清，立即进入 FAQ 或知识回答」。换题是否算「说清」由改写+分类结果判定，需用例覆盖。 |
| B. 上一轮是反问则强制计入同一链路 | 规则更死板，AC-022 更好测。员工换题若仍被当成补全，可能继续反问或在第 6 句被兜底，体验差。 | 实现简单，但和「说清就检索」在换题场景容易打架。 |

- **建议及理由**：选 A。5 轮上限是为了避免无限反问，不是为了拦住已经清楚的新问题。
- **最终选择与确认依据**：A。2026-09-12 用户回复「1.A 2.B 3.A 4.A」。确认上下文：主智能体就四项体验取舍征询用户后回传本实例。
- **落地与验收**：API-010 在改写+分类后，若本轮将走 FAQ / 闲聊 / 知识回答 / 超范围兜底（即不是反问），则 `clarification_round=0`；仅当本轮仍是反问时累加。AC-022 仍用连续 6 次含糊：第 1–5 次反问，第 6 次兜底。测试尚未执行。
- **复议条件**：分类经常把含糊追问误判成全新问题，导致 5 轮上限被绕过。

## D-005 知识库分块只读预览，不可编辑

- **日期与状态**：2026-09-12；已确认。
- **关联**：REQ-002；AC-024；API-005、API-006；tech-spec §二 API-005、§三 `ChunkPreview`、§五入库切块。
- **问题与体验影响**：用户在知识库原型上反馈，上传后看不出分块策略是否执行、也没有分块预览。这是已确认方案之外的用户可见能力。若做成可编辑，会改变入库切块与向量的一致性。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 只读预览实际落库分块 | 入库完成后能按序号看到标题路径和正文，以及「按标题/段落、800 字、重叠 80 字」的说明。不能在页面改分块。改标签仍写回各块标签、不重切。入库中/失败没有预览。 | 与现有 `CHUNK_MAX_CHARS` / `CHUNK_OVERLAP_CHARS` 一致；详情读库，列表只给 `chunk_count`。 |
| B. 页面上可改分块正文 | 用户可微调切块，但要重算向量、处理重叠与召回一致性，范围超出「预览」。 | 用户只要求预览，不要求改分块。 |

- **建议及理由**：选 A。满足「看出怎么切的」，不把切块做成编辑器。
- **最终选择与确认依据**：A。2026-09-12 用户在知识库原型明确要求预览；主智能体采用「只读、不编辑」边界并回传本实例，不再作为待决项。
- **落地与验收**：API-005 `ready` 返回按 `position` 升序的全部 `ChunkPreview`；页面只读渲染。测试尚未执行（对齐 PRD AC-024）。
- **复议条件**：后续明确要求在页面上改分块或重切。

## D-006 未确认工单何时根据对话抽取

- **日期与状态**：2026-09-22；已确认。
- **关联**：REQ-005、REQ-008；AC-030～AC-032；API-010（已转人工副作用，不改其成功/失败语义）、API-013、API-014；tech-spec §二 API-013/014、§五抽取合并。
- **问题与体验影响**：转人工后客服端已按 D-003 约 3 秒拉会话。工单预填若跟每次拉取同步调模型，坐席会反复等待且产生重复费用。用户后来说了新地址或改金额时，表单是自动变、要点按钮，还是打开会话时卡住等抽取结束，会改变操作节奏。坐席已经手改过的字段，要不要被后一轮对话盖掉。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 打开或拉工单时同步抽取 | 选类型或刷新时页面卡住等到百炼返回（约数秒到 45 秒）。若跟 3 秒轮询绑定会反复付费、表单闪动。实现简单。 | 与已确认的拉取间隔冲突大；不建议把 LLM 放进 GET。 |
| B. 后台抽取，GET 立刻返回当前草稿 | 选类型或用户新发言后，表单先显示上一版或待补全，`extract_status=extracting`，约数秒后拉取到新预填。手改字段（`agent_edited`）不被抽取覆盖；用户后说只更新未手改字段。坐席可在抽取失败时手填。 | 对齐 D-002 后台任务和 D-003 拉取；每条新员工消息最多触发一次抽取。费用随对话轮次增加，待真实验证。 |
| C. 仅坐席点「刷新抽取」 | 费用和时机完全由坐席控制。若忘记点，AC-031/032「后说自动补上/改掉」不会发生，除非产品改成必须点按钮。 | 少一次自动付费；要改验收表述或接受测案里先点刷新。 |

- **建议及理由**：选 B。产品要求未确认草稿随后说更新，又要求客服端定时拉会话；GET 不阻塞才能和 3 秒拉取共存。用 `agent_edited` 保护手改，避免正在改的金额被下一次抽取打回。放弃 A 的重复等待，放弃 C 与「后说自动更新草稿」的字面冲突。
- **最终选择与确认依据**：B。2026-09-22 用户确认「1.B」。
- **落地与验收**：API-013 不调模型；选类型与新消息投递后台 EXT-001；手改字段（`agent_edited`）不被覆盖；AC-031/032 在 `extract_status=ready` 后对照。测试尚未执行。
- **复议条件**：抽取经常把后说漏掉，或费用明显高于预期。
- **2026-09-23 部分替代**：后台抽取时机仍为 B。候选 C 中「后说自动改掉」以及本节「后说覆盖先说」已由确认 PRD AC-032 替代为「冲突保留原值」，见 D-008。AC-031 仍是缺失后续补为已填，不是覆盖已有值。

## D-007 已确认工单如何再次允许更新

- **日期与状态**：2026-09-22；已确认。
- **关联**：REQ-005；AC-030、AC-033；API-014、API-015；tech-spec §五 API-015。
- **问题与体验影响**：确认后字段默认不再被抽取覆盖。PRD 还写「除非坐席再次允许更新」。坐席纠正已确认工单时，是只能手改、要先解锁再抽，还是撤销确认回到草稿，会改变误确认后的恢复步骤。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| A. 确认后抽取不再跑；仍可 PATCH 手改字段和业务线；不能改类型 | 误填靠坐席对着对话改。没有「按新对话重抽」按钮，实现最少。 | 满足「默认不覆盖」；「再次允许更新」解释为手改。 |
| B. 增加「允许按新对话更新」动作 | 打开后对未手改字段再抽，已确认状态可保持或改回草稿。多一个控件和状态。 | 更贴近「允许更新」的字面；阶段 B 要加按钮。 |
| C. 「撤销确认」回到草稿 | 之后抽取与未确认规则恢复；误确认可整单重来。已确认瞬间对报表/后续流程的含义变弱。 | 本轮工单只存本系统、无外部同步，撤销代价低，但多一个破坏性操作。 |

- **建议及理由**：选 A。本轮没有外部工单系统，坐席手改足够纠正；少一个解锁状态可避免和「已确认后再打开仍是确认值」（AC-030）打架。需要重抽时再复议 B/C。
- **最终选择与确认依据**：A。2026-09-22 用户确认「2.A」。
- **落地与验收**：确认后新员工消息不投递抽取；API-014 改类型返回 409；手改字段仍 200。AC-030 确认后再打开值不变。测试尚未执行。
- **复议条件**：现场经常确认后用户又改地址/金额，手改来不及。
- **2026-09-23 对齐**：确认 PRD AC-047 写死「确认后新消息不再自动改字段、不能改工单类型」，与选择 A 一致，不重开。

## D-010 检索融合权重与合规拦截告警阈值
